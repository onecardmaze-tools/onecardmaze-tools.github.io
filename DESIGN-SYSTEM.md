# Design system and process

This is the contract for every change to the helper's interface. It is written
for people and coding agents who are not UI specialists. If you follow the
rules and the process below, your change will fit; if a rule blocks something
you need, change the rule here first, in the same pull request, and say why.

Source of truth, in order: this file → `companion.css` tokens → `uiMode()` and
`uiInsets()` in `index.html` → `tests/ui-states.cjs`. The history of the
owner's decisions is in [UI-DESIGN-NOTES.md](UI-DESIGN-NOTES.md).

## Principles

1. **The map gets the screen.** Current card / Cards is the top-left chip;
   Map is the top-right chip. A quiet unofficial About link sits below the card
   chip. Keep walking chrome within the budgets below. Desktop may expose a
   narrow map shortcut rail; phone secondary actions use a sheet.
2. **One task dock.** Walking and review use the same bottom region. Review
   retains its timeline and controls when paused or finished. On portrait phones
   the timeline gets its own full-width row; never shrink labels to fit one row.
3. **Reviewing never edits.** Playing, reversing, seeking, step inspection and
   map taps preserve the recording. A map tap during playback only pauses it;
   paused/finished map taps do nothing. Q/E also do nothing while reviewing.
   Only **Continue from here** may initiate a branch, with a confirmation when
   it would replace the later route. **Back to walking** returns to the route end.
4. **Undo means one action.** Each click movement and each rotation has a compact
   checkpoint. Undo restores its exact start, including an interrupted movement
   and consecutive rotations at the same point. Checkpoints persist with progress
   and backups. Old recordings without checkpoints fall back to recorded vertices.
   Holding Z does not continuously rewind. Start over remains undoable by toast.
5. **Quietly unofficial.** Keep the small unofficial About link visible during
   play. Use no game artwork, marketing header, or official branding.
6. **Colour means something.** Amber is reserved for "where you are in the
   route" (timeline progress and thumb). Blue-teal marks flips on the timeline.
   Olive edges and pale fills are the neutral UI. Red-brown is only for
   Start over.
7. **Hand-drawn, not childish.** Slightly uneven corner radii, a tiny tilt on
   the two rotate buttons and the primary intro button, offset shadows, and the
   Patrick Hand face for titles and the identity chip. Body text and controls
   stay in the system sans-serif for legibility. Don't add more decoration.
8. **English, plain and short.** See Copy below.

## Modes

`uiMode()` in `index.html` returns one of five modes and writes it to
`body[data-mode]`. CSS shows each dock with `body[data-mode=…]` selectors,
which also removes hidden controls from the tab order. When the mode changes and
the focused control disappears, focus moves to the new mode's primary control
(`modePrimary`).

| Mode | When | Dock | Primary | Map tap | Esc |
| --- | --- | --- | --- | --- | --- |
| `walk` | Exploring | Rotate left · Undo · Replay · Rotate right | Replay | Choose start / walk | — |
| `playing` | A replay runs | Back to walking · Reverse/Pause · Play/Pause · timeline · Speed · disabled inspection row | Pause | Pause | Back to walking |
| `paused` | Inspecting a recorded position | Same transport + Previous step · Next step · Continue from here | Play | No change | Back to walking |
| `complete` | Replay reached either end | Same transport and timeline; inspection stays available | Play | No change | Back to walking |
| `place` | Placing an annotation | Glyph · Tap the map to place it · Change style · Done | Done | Place, then return | Cancel |

- Replay starts immediately from the beginning when walking at the route end.
- Inspection steps move to adjacent recorded vertices; rotation/flip animation
  remains internal to playback. There is no user-facing event list.
- Continue from here asks **Keep route / Walk from here** before replacing future
  history. At the route end it returns directly to walking. The user then taps
  their next destination; an ordinary review tap never chooses a branch.
- Completion toasts say “Replay complete” / “Reverse replay complete”, never
  claim a maze solution. Manual card completion is a separate annotation.

To add a mode: add it to `uiMode()`, `modePrimary`, the CSS selectors, the
table above, and `MODE_CONTROLS` in `tests/ui-states.cjs`.

## Layout budgets and breakpoints

| Layout | Applies when | Chrome | Budget |
| --- | --- | --- | --- |
| Portrait phone | width ≤ 700 | Card / Map chips, walking dock; review timeline above controls and inspection | Walking dock ≤ 15% of height; 58px buttons |
| Narrow phone | width ≤ 360 | Same tasks; labels wrap in review; no tiny targets | Walking dock ≤ 16% of height |
| Short landscape | height ≤ 500, landscape | Walking side rails; compact two-row review transport | Walking rails ≤ 104px wide each |
| Tablet | width ≥ 701, height > 500 | Centred dock, wider review timeline, map popover | Walking dock ≤ 15% of height |
| Desktop | width ≥ 1000, height > 500 | Tablet layout plus right map shortcuts | Walking dock ≤ 12% of height |

Review reserves 220px at the bottom on phones, 164px on tablet/desktop and
148px in short landscape. Walking reserves 96px, or 12px with landscape rails.
The desktop map rail reserves 164px at the right. About sits below the top chip;
these limits describe dock coverage, not a sum of all floating element heights.

The camera has to know about the chrome. `uiInsets()` in `index.html` returns
the space reserved on each side, and **must match the `--inset-*` tokens** in
`companion.css`. `fitView()` fits the card inside the insets and `camTarget()`
keeps the walker out from under them. If you change the dock height, change
both, and run the browser QA.

Floating layers, from back to front: map canvases → chips and dock
(`--z-chrome`) → hint, confirm card and toasts (`--z-float`) → sheet scrim and
sheets (`--z-scrim`, `--z-sheet`) → import and intro (`--z-modal`). Floating
layers sit at `--inset-bottom` so they never cover the dock.

## Tokens

All values live at the top of `companion.css`. Use the token, not a literal.

- **Colour.** `--paper` (surfaces), `--bg` (page), `--fill` / `--fill-press`
  (primary and pressed controls), `--ink` / `--ink-2` / `--muted` (text, in
  decreasing emphasis; `--muted` is the lightest text allowed: 5.7:1 on paper,
  5.0:1 on `--fill`), `--edge` / `--edge-soft` / `--rule` (outlines and dividers),
  `--accent` (icons), `--link`, `--amber` / `--amber-ink` / `--track`
  (timeline), `--flip`, `--danger`, `--toast` / `--toast-ink` /
  `--toast-action`, `--focus`, `--scrim`.
- **Type.** `--hand` for titles and the identity chip only; `--sans` for
  everything else. Sizes `--t-xs` (12px, the floor) to `--t-title` (25px).
  Inputs use 16px so iOS doesn't zoom.
- **Space.** `--s1`…`--s5` (4, 6, 10, 14, 18px).
- **Size.** `--tap` 44px minimum for any control; text links at least 24px tall.
  `--dock-btn` 58px; `--rail-btn` 84px.
- **Shape.** `--r-control` 7/10/6/9px, `--r-surface` 10/14/9/12px, `--r-sheet`
  for the top of phone sheets. Uneven on purpose; don't "fix" them to one value.
- **Shadow.** `--shadow-control`, `--shadow-surface` (offset, flat, like paper)
  and `--shadow-float` (soft, for things that hover over the map).
- **Motion.** `--t-fast` 140ms, `--t-med` 220ms, `--ease`. All motion is
  removed under `prefers-reduced-motion`.

## Components

| Component | Markup | Use it for | Don't |
| --- | --- | --- | --- |
| Corner chip | `.chip.corner-left` / `.corner-right` | Current card / Cards (left), Map (right) | Put destructive controls on the map |
| Identity link | `.identity-link` | Quiet unofficial About entry | Compete with the card name |
| Map rail | `.map-rail` | Desktop shortcuts: position, fit, add marker | Show on narrow or short screens |
| Dock | `.dock` + mode modifier | The control area for the current task | Stack two docks; show a dock outside its mode |
| Dock button | `.dbtn` (icon above label, `kbd` hint on desktop) | Mode actions. `.rotate` for the two rotate buttons only; `.primary` for the one main action; `.row` for icon-beside-label in pills | Icon-only buttons; more than one `.primary` per dock |
| Timeline | `.timeline` with `#scrub` and `#eventTicks` | Route position. Label = percent + "of route" or the current event | Use amber anywhere else |
| Inspection row | `.review-actions` | Previous/next recorded step and explicit branching | Hide the timeline when playback finishes |
| Place bar | `#markerPlacementTip` | Marker placement mode | Keep the marker sheet open while placing |
| Hint chip | `.hint` | One-time teaching ("Tap the path to walk there"), retired after first use via localStorage | Permanent instructions; more than one hint at a time |
| Confirm card | `#confirmCard` via `askConfirm()` | A choice that would replace or discard work. Safe option first and focused, action second | "Are you sure?"; confirmations for undoable actions |
| Status toast | `#toast` via `toast()` | Short facts at the top (≈2.6s) | Instructions; anything the player must act on |
| Action toast | `#actionToast` via `actionToast()` | Undo after a destructive action (8s, with a draining timer) | Stacking several |
| Sheet | `.sheet` (Map tools, Markers, Backup) | Secondary actions. Bottom sheet on phones with a scrim; popover under Map on desktop. One open at a time | Putting walking controls in a sheet |
| List row | `.li` inside sheets; `.sec` section labels; `.hr` divider | Map actions, or current-card actions in the library; destructive items last | Mixing destructive and routine items |
| Segmented control / switch | `.seg`, `.switch` with `role=switch` and `aria-checked` | Zoom − Fit +; Show trail | Toggle buttons that only change colour |
| Modal panel | `#help` dialog, `#loader` / `#cardLibrary` overlays | Introduction, card import and saved-card selection. Bottom sheets on phones ≤ 520px | Long copy; more than one primary button |

Icons are inline SVG symbols at the top of `<body>` (`#i-*`), 2px round strokes
on a 24px grid. Reuse a symbol, or add one in the same style.

Your cards opens from the current-card chip and on return visits. Add cards is
the common entry for single and batch image import; backing out never changes
the active card. Current card options contains completion, Start over and backup.
The Map sheet contains position, markers, zoom/fit and trail visibility only.
A labeled Search cards input filters names instantly without changing the active
card or route; matching is case-insensitive and clearing restores the list.
Each row has a thumbnail, a named play button and a delete button. Names wrap;
the list scrolls within the modal. Import adds a new card only after both faces
are selected and the player chooses **Save and start**. Batch import reuses the
modal, image drop target and scrollable list. Names ending
in `_front` and `_back` pair automatically (case-insensitive); the shared name
names the card. Recommend number-first names such as `01-Forest_front.png` and
`01-Forest_back.png`; older names remain accepted. Only readable, unambiguous
pairs are imported. A single action
adds all ready pairs to Saved cards without switching the active card or editing
the route. Exact image pairs are skipped; different images with the same name
remain separate cards. Import progress and failures stay in the modal or library.
Opening import never discards work. Routes auto-save separately for each card, including
the practice card. Switching saves first and resumes the selected card; if saving fails,
ask before discarding the route. Current card options includes a reversible “Mark as completed”
switch. This is a player annotation, never an inferred game outcome. Saved-card rows
show Completed, Continue route or Not started below the name. Deleting a saved card
asks before removing its images, route, markers and completion mark. Progress is stored
locally in this browser; portable recording imports still require export to keep them.

## Copy

- English only. Sentence case. No exclamation points, no emoji.
- Name actions with verbs the player would use: "Rotate left", "Replay",
  "Replay again", "Done", "Start over", "Walk from here", "Keep route".
- Say what happened, then what you can do: "Route cleared · markers kept ·
  Undo".
- Don't claim game outcomes ("solved", "correct path") or authority
  ("official"). "Fan-made, unofficial" is the voice.
- Keyboard hints live in `kbd` and `aria-label` ("Rotate left (Q)"), never in
  sentences on screen.

## Accessibility

- Every control has a visible text label; icons are `aria-hidden`.
- Targets: 44×44px minimum; text links 24px tall. The QA script enforces this.
- Focus is always visible (`--focus` ring) and never lost: when a mode hides
  the focused control, focus moves to the mode's primary control. Opening a
  sheet focuses its first useful control; closing returns focus to its visible opener.
- Esc closes the top-most surface first (import, then sheets), then leaves
  review (Done) or placement.
- Contrast: body text ≥ 4.5:1, large text and UI outlines ≥ 3:1 on `--paper`.
- Keyboard: Q/E rotate, Z undo one action, Space/Shift+Space replay,
  F fit, T trail, H about, R start over (undoable), + / − zoom. No WASD or arrow
  movement, by design.
- Respect `prefers-reduced-motion`; respect safe-area insets.

## Process

Follow these steps for any UI change, however small.

1. **Name the job.** Write one sentence: who is doing what, in which mode.
   If the change doesn't belong to a mode, it belongs in Map / Your cards.
2. **Check the budget.** Decide where it goes using the Modes table and Layout
   budgets. If it adds height to a dock or a new floating element, find
   something to remove or make it mode-specific.
3. **Reuse before inventing.** Use an existing component and tokens. A new
   component needs a row in the Components table.
4. **Write the copy** using the Copy rules, including the `aria-label`.
5. **Implement.** Visibility goes through `body[data-mode]`, not ad-hoc
   `hidden` toggles in the engine. Keep layout numbers in tokens; if the
   camera needs them, update `uiInsets()` too.
6. **Test.**
   - `node tests/ui-mode.test.js` and the other `tests/*.test.*` files.
   - `node tests/ui-states.cjs` (needs Playwright). It visits every mode at
     320×568, 375×667, 390×664, 844×390, 667×375 and 1280×800 and fails on
     wrong controls, overlap, small targets, clipped labels, budget overruns,
     lost focus, page errors, or a route edited by reviewing.
   - `node tests/ux-layout.cjs` checks camera/CSS insets in 35 mode/viewport combinations.
   - Look at the screenshots it writes. Automated checks miss ugly.
   - On a real phone if you can (iOS Safari and Android Chrome), especially for
     safe areas and the on-screen keyboard.
7. **Update the docs**: this file if a rule changed, README's controls table if
   behaviour changed, and bump the `?v=` query strings and `app-version` meta in
   `index.html` so returning visitors get the new CSS and JS.

### Pull request checklist

- [ ] The change fits a mode in the Modes table (or Tools), and the table is
      still true.
- [ ] Portrait walk chrome is still ≤ 15% of the height (see QA output).
- [ ] Only tokens; no new literal colours, radii or z-indexes.
- [ ] Every new control has a text label, a 44px target and an `aria-label`
      with its shortcut.
- [ ] Reviewing still can't edit the route; anything destructive is undoable
      or asks first.
- [ ] Copy is English, sentence case, no "official", no outcomes.
- [ ] `tests/ui-states.cjs` passes and the screenshots look right at 320px,
      landscape and desktop.
- [ ] Cache-busting versions bumped.
